# Publishing a module to the marketplace

The marketplace a site installs from is `module-marketplace/` on `main`: one ZIP per module and an `index.json` catalogue, served from `raw.githubusercontent.com` unless an installation points `BLYSIS_MARKETPLACE_BASE` somewhere else. A change merged to `module-sources/` reaches sites only through those files.

## After editing a module

```bash
npm run validate:module module-sources/<id>
npm run build:marketplace
```

Bump `version` in the module's `module.json` in the same change: a patch for a fix, a minor for a feature. Sites are offered an update only when the catalogue's version is newer than the one they run, and a module keeps its catalogue date until its version moves.

Commit the source, its ZIP and `index.json` together. `scripts/check-marketplace-sync.ts` runs in CI and fails when an archive or the catalogue disagrees with `module-sources/`.

## What the build does

`scripts/build-marketplace.ts` reads every `module-sources/<id>/module.json` and refuses the whole catalogue, writing nothing, when a module imports core internals (`@/core/lib`, `@/core/components`) or listens to a hook that nothing emits. Then it writes each archive, and only those whose contents changed: a rebuild of an unchanged module leaves its ZIP byte for byte as it was, whichever machine runs it. A written archive is the same bytes for the same files every time; `scripts/lib/deterministic-zip.ts` says why each field is what it is.

The catalogue carries each module's name and description in every locale, because a site shows the marketplace before the module, and its strings, are installed.

`module-marketplace/manifest-schema.json`, the grammar every manifest is checked against, is regenerated by the same command.
